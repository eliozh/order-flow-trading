# Order Flow Trading v0.1.0 — release and operations plan

**Scope**: local, single-operator, paper-trading terminal distributed as source.
**Version**: `0.1.0` (`pyproject.toml`, `src/oft/__init__.py`).

## What "deploy" means here

There is no hosted service and no artifact registry for this release. "Deploy"
means installing or upgrading the source checkout on the operator's own machine.
"Roll back" means checking out the previous source version and restoring the
SQLite snapshot taken before the upgrade migrated the database.

## Prerequisites

- Python 3.12 and [uv](https://docs.astral.sh/uv/)
- Node.js 20+ and npm (CI uses Node 22)
- A git checkout of the repository and enough disk for `$OFT_DATA`
- Linux is the exercised platform; no native installer or service unit ships

## Install (fresh machine)

```bash
cp .env.example .env          # optional: defaults are paper + loopback
uv sync
npm --prefix web install
npm --prefix web run build    # writes web/dist, served by FastAPI
```

`uv sync` installs the locked Python dependencies and the `oft` console script.
`npm --prefix web install` is enough for development; run the build when the
daemon should serve the compiled SPA.

## First run / onboarding

```bash
uv run oft init               # optional interactive onboarding, daemon down
uv run oft daemon start       # full runtime; blocks in the foreground
```

`oft init` persists the scan period, watchlist, LLM provider/key (read from
stdin, never argv), budget thresholds, and the optional Telegram channel. It can
be resumed with `oft init --resume`. On first daemon start, `$OFT_DATA/oft.db`
is created and migrated to the current schema.

Run `oft daemon start` under the operator's own supervisor or in a terminal.
There is no bundled systemd unit; ADR-0012 shows the intended unit shape with
`ExecStart=/path/to/oft daemon start`.

## How to run

```bash
uv run oft daemon start       # API + scan/trigger/monitor/management schedulers,
                              # live WS ingestion, and Telegram
uv run oft serve              # HTTP API/UI only; no schedulers or ingestion
```

Both bind `127.0.0.1:7611` by default. `oft serve` reports not-ready in a real
environment because `/ready` requires a fresh scheduler heartbeat; use
`oft daemon start` for a working paper runtime.

Lifecycle and inspection:

```bash
uv run oft daemon status
uv run oft daemon logs --lines 100
uv run oft daemon stop
```

## Where data lives

Default `$OFT_DATA` is `./data`; `OFT_DATA_DIR` and `OFT_DATA` are accepted.

| Path | Contents |
|---|---|
| `$OFT_DATA/oft.db` | SQLite state: config, scans, opportunities, orders, positions, trades, audit chain, prompts, migrations |
| `$OFT_DATA/market/` | Immutable Parquet parts (aggTrades, klines, mark price, liquidations) |
| `$OFT_DATA/backups/` | Manual `oft backup` files, `pre-migration-*` and `pre-restore-*` snapshots |
| `$OFT_DATA/logs/daemon.log` | Structured daemon log, 50 MB × 5 rotations, mode 0600 |
| `$OFT_DATA/run/` | `api-token` (0600), `daemon.pid`, scheduler heartbeat |
| `$OFT_DATA/knowledge/` | Private compiled playbook, gitignored |

The data directory and `run/` are private (`0700`). Backups contain database
files only; secrets are never included.

## Secrets

No secret is needed for paper market data, local scans without an LLM, or the
loopback API. The API bearer token is generated into
`$OFT_DATA/run/api-token` (0600) on first start unless `OFT_API_TOKEN` is set.

| Secret | When required |
|---|---|
| `OFT_TELEGRAM_BOT_TOKEN`, or `oft telegram token set --stdin` | Telegram channel |
| `OFT_OPENAI_API_KEY` / `OFT_ANTHROPIC_API_KEY` / `OFT_DEEPSEEK_API_KEY` | The selected LLM provider (`stub` needs none) |
| `OFT_MASTER_KEY` (at least 32 characters) | Encrypted-file fallback only when no OS keyring is available |
| `OFT_BINANCE_API_KEY` / `OFT_BINANCE_API_SECRET` | Not used by shipped code; reserved for a future live path |

Stored secrets prefer the OS keyring, then `$OFT_DATA/secrets.enc` when
`OFT_MASTER_KEY` is set. Without either, key writes are refused. Never commit
real credentials; `.env` is local input, not a secret store.

## Backup and restore

```bash
uv run oft backup                          # -> $OFT_DATA/backups/oft-<UTC>.db + .sha256
uv run oft backup --out /path/to/disk      # off-machine copy
uv run oft backup --json

uv run oft daemon stop
uv run oft restore "$OFT_DATA/backups/oft-<UTC>.db" --yes
```

`oft backup` writes a verified `VACUUM INTO` copy with a SHA-256 sidecar and may
run while the daemon is up. `oft restore` verifies integrity and the sidecar,
refuses while the daemon is running, and writes a `pre-restore-*` safety
snapshot before swapping the database. Use `--no-snapshot` only when the current
database is already unusable.

Backups are **not encrypted** and scheduling plus the 7-daily / 4-weekly /
12-monthly retention policy are **not automated**. Put a daily `oft backup` in
the operator's scheduler and copy it off the machine; `oft doctor` reports the
backup age and degrades beyond 48 hours.

## Upgrade procedure

```bash
uv run oft daemon stop
uv run oft backup --json
git fetch --tags
git checkout <target-release-tag>   # target release commit
uv sync
npm --prefix web install
npm --prefix web run build
uv run oft daemon start             # applies pending migrations
uv run oft doctor
uv run oft scan run --symbol BTCUSDT --metrics-only --json
curl -sS http://127.0.0.1:7611/ready
```

Migrations are forward-only, numbered, transactional, and applied by the daemon
on start. Before touching an existing database, the daemon writes and verifies
`$OFT_DATA/backups/pre-migration-<old-schema-version>-<UTC>.db` (keeping the
latest 10). If that snapshot cannot be created, the daemon refuses to start. A
failed migration rolls back and refuses to start on a partial schema rather than
running damaged. `oft doctor` must be `READY` before the terminal is left
unattended.

## Rollback procedure

Rollback applies to an upgrade, not to first installation. If the new version
never started (no migration), reinstall the previous checkout and start it. If
the new version migrated the database, restore the pre-migration snapshot.

Rehearsed-rollback checklist — rehearse it once against a scratch data directory
before the first real upgrade, then run each step and stop on an unexpected
error:

```bash
# 1. Stop the failed runtime and confirm it is down.
uv run oft daemon stop
uv run oft daemon status

# 2. Check out the previous release and rebuild the previous code.
git checkout <previous-release-tag>
uv sync
npm --prefix web install
npm --prefix web run build

# 3. List the snapshots and pick the pre-migration one from the failed upgrade.
ls -lt "$OFT_DATA"/backups/pre-migration-*.db

# 4. Restore it (refused while a daemon is running; keeps a pre-restore snapshot).
uv run oft restore "$OFT_DATA/backups/pre-migration-<old-schema-version>-<UTC>.db" --yes

# 5. Verify the database, audit chain, and configuration with the daemon down.
uv run oft doctor

# 6. Start the previous version and confirm liveness and readiness.
uv run oft daemon start
curl -sS http://127.0.0.1:7611/health
curl -sS http://127.0.0.1:7611/ready

# 7. Confirm the paper runtime end to end.
uv run oft status
uv run oft scan run --symbol BTCUSDT --metrics-only --json
```

If the snapshot is missing because the upgrade failed before migration, skip
step 4 and use the manual backup from the upgrade procedure. If restore rejects
the file, do not force it: `oft restore` validates integrity and the sidecar and
reports `BACKUP_INTEGRITY_FAILED` or `BACKUP_HASH_MISMATCH`. Restoring the
snapshot also discards paper state written after the snapshot was taken, which
is the intended rollback boundary.

## Health checks

| Check | Command | Meaning |
|---|---|---|
| Liveness | `curl -sS http://127.0.0.1:7611/health` | Process is up; no dependency or auth required |
| Readiness | `curl -sS http://127.0.0.1:7611/ready` | Config, SQLite, schema, disk, Parquet, clock, market data, and scheduler heartbeat; 503 when not ready |
| Diagnostics | `uv run oft doctor` | Same checks without the daemon, plus audit chain, stale jobs, orphan Parquet rows, backup age, kill switch |
| Runtime | `uv run oft daemon status` / `uv run oft status` | PID, next/last scan window, positions, budget, surfaces |

`oft doctor` exits 0 even when the daemon is offline and the report is
`DEGRADED`; read the per-check status rather than the exit code alone.

## Explicitly out of scope for v0.1.0

- **Live trading.** Every non-`PAPER` execution intent is refused; there is no
  live arming, exchange order submission, or user-data stream.
- **Hosted deployment.** No cloud/managed service, containers, or remote
  multi-user access; the daemon is loopback-bound by default.
- **Native mobile apps.** The read-only Telegram channel is the mobile surface;
  no iOS/Android client ships.
- **Automated backup operations.** No scheduling, encryption at rest, retention
  enforcement, or offsite replication — all operator work.
- **Automatic updates or silent migrations.** Upgrades are deliberate, manual,
  and always preceded by a verified snapshot.
- **Binance credentials.** Accepted by the settings model but unused by the
  shipped public market-data path.
- **Native packaging/installers.** Distribution is a source checkout built with
  `uv` and npm.

## Release gate

The release commit must pass the same offline gate as CI (`make ci`): ruff,
mypy, import-linter, fixture checksums, pytest with the 80% coverage floor,
frontend lint/typecheck/tests/build. The `0.1.0` version is recorded in
`pyproject.toml` and `src/oft/__init__.py`.
