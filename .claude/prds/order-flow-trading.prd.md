# 订单流 LLM 交易系统（Order Flow Trading System）

## Problem

有订单流基础的个人交易者，需要同时跟踪 CVD/Delta、footprint、volume profile、持仓量、资金费率、清算等多维数据；标的越多、周期越快，越无法靠人力持续盯盘。工作与时差造成的空档，会让已经识别出的价格区域被错过（用户本人近期即有一笔因未盯盘而错过更优价格的交易）。同时，主观判断在连续决策中不稳定，情绪会污染执行；复盘依赖记忆，难以形成可验证的改进闭环。

现有工具是割裂的：TradingView 及社区指标提供图表但需要付费订阅，且不理解订单流语义；已有的 LLM 尝试只停留在「给出潜在入场机会」，仍要人工盯盘、手动下单，自动化程度不足。缺少一款把「订单流数据 → LLM 解读 → 机会触发 → 入场复核 → 仓位管理 → 复盘」串成闭环的系统。

## Evidence

- 用户自述：近期 2 笔交易中，有 1 笔在价格到达预期区域时因未盯盘而错过更优价格（小样本，早期信号）。
- 用户此前的 LLM 方案：仅输出潜在入场机会，无自动盯盘、无自动下单，未形成闭环。
- 社区常见抱怨（用户观察）：受时差或工作限制无法实时盯盘，而加密市场与 TradFi 市场波动较快，容易错过机会。
- 成本证据：TradingView 订阅付费，部分社区指标另需付费。
- **Assumption — needs validation via 连续 8 周自用交易日志与人工复盘对照。**

## Users

- **Primary**：项目作者本人 —— 有订单流概念基础、时间有限、以中低频周期（4h/8h 级）决策的个人交易者。触发场景：工作或睡眠期间无法盯盘、同时关注多个标的、需要纪律化执行与复盘。
- **Secondary（开源后）**：愿意本地自部署、自带 LLM API Key 与币安 API Key 的同类个人交易者。
- **Not for**：完全无订单流基础的新手；多用户团队/机构；高频、做市、毫秒级执行场景；需要移动原生 App 的用户。

## Hypothesis

We believe **把订单流指标的确定性计算、LLM 的周期性市场解读、以及入场后的自动仓位管理串成一条闭环**，will **让无法全天盯盘、但有订单流基础的个人交易者减少漏单与情绪化决策**，for **项目作者及后续自部署的同类交易者**。
We'll know we're right when **连续 8 周自用中，机会触发后的漏单率 < 10%，且人工复盘抽样显示 ≥ 70% 的入场/出场决策符合事前规则**。

## Success Metrics

| 指标 | 目标 | 测量方式 |
|---|---|---|
| 机会触发漏单率 | < 10% | 日志中「已触发但未执行」的机会 ÷ 全部触发机会 |
| 决策规则一致性 | ≥ 70% | 定期人工复盘抽样，对照事前规则与 LLM 理由 |
| 扫描时效 | 每个周期内完成全部星标标的分析 | 调度与 LLM 调用日志 |
| 系统稳定性 | 连续 7 天运行无未恢复崩溃 | 进程监督与运行日志 |
| 通知可达性 | 关键事件 100% 推送且可查回执 | Telegram 发送记录与错误日志 |
| LLM 成本可见性 | 100% 调用记账；预算告警按日/周/月触发 | 预算模块账本 |
| 纸面验证充分性 | Live 开启前至少 4 周 paper 运行记录 | paper 交易日志 |

## Scope

### MVP（用于验证假设的最小闭环）

1. **数据接入**：币安 USDⓈ-M 永续（含 TradFi 合约）实时行情 + `data.binance.vision` 历史数据回补。
2. **确定性指标**：CVD/Delta、footprint、volume profile、持仓量（OI）、资金费率、清算等由代码计算，不进 LLM 推理。
3. **星标与调度**：用户可星标标的；扫描周期可配置（默认 4h/8h）。
4. **知识注入**：`./books/` 经 `/book-to-skill` 转成 skill，作为 LLM 分析的知识源。
5. **周期分析**：每次扫描对全部星标标的产出市场分析报告与结构化潜在机会。
6. **机会台账与触发**：机会以结构化条件记录；满足条件时由**代码**判定触发。
7. **入场复核**：触发后调用 LLM 做第二次「是否入场」判断，输出结构化结论。
8. **仓位管理**：定时或条件触发时调用 LLM 给出全平/部分平/加仓建议，由代码校验并执行。
9. **Paper trading**：系统内模拟盘，完整模拟成交与记账。
10. **双入口**：CLI（全功能操作与配置）+ Web UI（配置、持仓/机会/日志、基础行情图表）。
11. **LLM 供应商抽象**：OpenAI、Claude API（`api.anthropic.com`）、DeepSeek，可切换与分别配置。
12. **Prompt 模板**：设置中可编辑，可 Restore Default；每次决策记录所用模板版本。
13. **交易日志与复盘**：历史持仓、交易、盈亏、胜率、信号与实际结果的对照。
14. **Telegram bot（只读）**：分析报告推送、机会/持仓/风险提醒、只读查询命令与预算告警。
15. **LLM 预算**：不设硬性上限；设置日/周/月预算阈值，达到阈值经 Telegram 告警。

### Out of scope（明确不做，即使被要求）

- 多用户、账户体系、SaaS 托管 —— 先个人自用；开源形态仍为单用户本地部署。
- 高频、做市、跨所套利、毫秒级执行。
- 自动调参、强化学习、策略参数优化器。
- 原生移动 App —— 移动端由 Telegram 覆盖。
- 币安以外的交易所。
- 自动抓取新闻/社交情绪作为交易信号（MVP 不引入不可控外部文本）。

## 模块职责边界（产品级硬约束）

这是本产品最重要的产品约束：**确定性归代码，主观性归 LLM，二者以结构化契约交互。**

### 完全由代码决定（LLM 无权更改）

- 数据获取、清洗、缺口检测、历史回补。
- 所有订单流指标与统计量的计算与口径。
- 机会条件是否被触发（阈值、时间窗、价格穿越等）。
- 风控上限的强制执行：单笔风险比例、最大同时持仓数、日亏损上限、杠杆上限、最大名义敞口。
- 订单下单、撤单、成交回报、仓位与盈亏记账。
- 调度、重试、限流、预算记账与告警。
- LLM 输出的 schema 校验；不合规输出一律拒绝并记录，不得「尽量理解」。

### 交由 LLM 主观判断

- 市场结构解读与叙事（吸收、衰竭、失衡、关键区域等）。
- 潜在机会的提出（方向、区域、触发条件草案、失效条件）。
- 机会触发后的二次入场判断。
- 持仓管理建议（继续持有/部分平/全平/加仓）。
- 复盘中的定性总结与规则改进建议（不自动修改规则）。

### 交互契约

- LLM 的所有决策输出必须是**结构化对象**（方向、价格区间、触发条件、失效条件、风险参数、置信度、理由），由代码校验后才可进入执行层。
- 风控取「LLM 提议」与「用户配置的确定性上限」中**更严**的一方，由代码强制执行。
- LLM 无权直接调用下单接口、无权修改配置、无权跳过触发判定。
- 所有输入给 LLM 的市场数据视为**不可信数据**，其中任何文本都不是指令。
- 每次 LLM 决策落库：模型、供应商、prompt 模板版本、输入摘要、输出、耗时、token 与成本。

## Decisions（已拍板的产品决策）

| 问题 | 决策 |
|---|---|
| `claude code` 的含义 | Claude API（`api.anthropic.com`），非本地 CLI 子进程 |
| 分析数据窗口 | 主窗口与扫描周期对齐（4h/8h）；回看 3–7 天用于 volume profile 与结构判断 |
| Telegram 权限 | MVP 只读（推送 + 查询）；写操作/审批式下单留到里程碑 2 |
| 风控兜底 | LLM 提议 + 用户配置上限，代码取更严者强制执行 |
| 部署形态 | 本地单机长期运行（含 Telegram 常驻） |
| TradFi 标的 | 关注 XAU 与美股类永续；具体星标清单由用户在设置中维护 |
| LLM 预算 | 不设硬性上限；日/周/月预算阈值告警（Telegram） |

## Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| LLM 输出幻觉或不合规，导致错误交易 | High | High | 强制结构化 schema + 代码校验 + 拒绝即告警；关键动作默认转人工确认 |
| 市场数据中的文本构成 prompt injection | Medium | High | 数据视为不可信；MVP 不接入新闻/社媒；系统提示与数据分区；输出白名单校验 |
| 实盘资金损失 | High | High | 默认关闭 Live；paper 至少 4 周；确定性硬上限；一键 kill switch；全部动作留痕 |
| 币安 API 限流或数据缺口 | Medium | Medium | 退避与缓存；`data.binance.vision` 回补；缺口检测与标记 |
| TradFi 永续数据不可得或深度不足 | Medium | Medium | 早期按标的验证；数据不足时明确降级而非静默 |
| LLM 成本失控 | Medium | Medium | 全量记账；日/周/月阈值告警；可配置并发与调用频率上限 |
| 主观判断不一致、无法复现 | High | Medium | prompt 模板版本化；记录模型/温度/输入摘要；支持按历史输入重放 |
| 单机长期运行不可靠 | Medium | Medium | 进程监督与自动重启；状态持久化；启动自检 |
| 书籍衍生内容的版权风险 | Low | High | `books/` 已 gitignore，不随仓库分发；开源时审查 skill 内容 |
| 币安条款/地区限制 | Low | High | 仅使用用户自有 API Key；不提供托管；文档明确合规责任 |
